# 项目整体 Review 与后续开发基线

审查日期：2026-10-29。代码基线：`dev` / `2bfa912`。开始审查时工作区干净。

本次检查覆盖后端、worker、前端、构建与升级脚本、配置、部署清单、现有测试和项目文档。未连接生产 Redis、集群、镜像仓库或 OSS 验证现网状态；涉及部署的结论针对仓库提供的配置与操作路径。本次只新增本文，没有修改业务代码、部署配置或运行数据。

## 1. 总体判断

现有架构可以继续沿用，适合当前内部小规模使用。Web 负责入队、worker 串行执行、Redis 保存任务状态、任务独立临时目录、归档原子替换，这些边界值得保留。暂时没有必要更换队列框架、重写前端或整体拆分 app.py。

主要风险集中在最近从“单节点共享目录”迁移到“skopeo + OSS + 多节点 worker”之后，成功、下载、清理和发布之间的约定没有完全同步；另外，正常路径单测较多，异常退出、重复执行和真实外部工具边界覆盖不足。

下面列出 6 项 P1 和 7 项 P2。P1 表示下一轮应优先修复，不表示已确认发生线上事故。另列已有问题与待环境验证项，避免把推测当作现网事实。

## 2. 实际架构与开发入口

```text
浏览器工作台
  ├─ POST /build：创建任务
  ├─ GET /build?task_id=...&since=...：SSE 观察
  └─ /tasks/overview：轮询任务中心
             │
         Flask / gunicorn（app.py）
             │
         Redis：meta / logs / queue / processing / slot / heartbeat
             │
         worker.py：单进程串行消费，多个副本并行
             ├─ patch 模式：OSS 版本列表 → nuwa 差异清单
             ├─ custom 模式：用户镜像清单
             └─ pull_save.sh → skopeo docker-archive → tar.gz → OSS
                                                          │
                        Web 下载入口 ← 302 签名下载地址 ───┘
```

| 领域 | 主要入口 | 继续开发时应维持的约定 |
|---|---|---|
| 任务提交/API | app.py 的 `_create_build_task()`、`api_build_post()` | POST 创建、GET 观察；保留旧接口兼容时避免 SSE 重连重复入队 |
| 执行与恢复 | worker.py 的 `process_task()`、`reclaim_stale_tasks()` | 心跳、processing、slot、取消必须一起考虑；保留失活 slot 清理 |
| 构建与交付 | app.py 的两条 `run_build_task*()` | 两种模式最终应执行一致的归档、上传、完成与清理规则 |
| 镜像引用 | pull_save.sh | 前端、后端、脚本对合法引用、去重和输出文件的理解必须一致 |
| 前端状态 | static/app.js | 区分任务执行状态和观察连接状态；通过 task_id 恢复 |
| 发布 | config.yaml、apply YAML、redeploy.sh | 配置与镜像必须能从仓库确定性重建 |

当前有五条 patch 版本线：6.4.9、6.5.9、6.6.9、7.0.9、7.1.9；代码中的 `task_type=v6` 表示按 patch 差异构建，`v7` 表示自定义清单，不能再把它们完全等同于产品大版本。前端已有 mode/channel 语义，后续应沿用。

`config.yaml` 配置为 OSS、并发 3、上传后删除本地副本。部署清单配置三个 worker，使用 skopeo、独立 emptyDir 产物目录、节点本地 nuwa 缓存；app 仍挂旧包 PVC 并固定在 apk01，Redis 仍为单节点 PVC + AOF。三个 worker 并不意味着 Redis 已具备高可用能力，调度约束也只是尽量分散，并非保证每节点恰好一个。

## 3. P1：优先修复

### R1. 清理单测可能删除真实 OSS 对象

- 位置：`tests/test_app_logic.py:91`、`:587`、`:604`；调用链为 `app.py:946` → `delete_oss_package()`。
- 条件：按当前仓库 OSS 配置运行单测，且运行环境中的 ossutil 可执行、凭据有效。
- 问题：测试只替换本地包目录和保留配置，没有统一隔离存储后端。测试创建的 `deepflow_patch_v669_01_02.tar.gz` 等名字会被用于真实 OSS 删除请求。
- 证据：拦截 `_run_ossutil()` 后运行五个保留策略用例，捕获到 9 次远端 `rm` 调用，目标前缀来自当前业务配置。本机首次检查因仓库 ossutil 是 Linux 二进制而无法执行；后续验证均阻断外部调用。
- 建议：测试默认强制本地存储，统一 mock 外部命令；OSS 用例显式启用模拟后端，禁止漏出的外部写操作。
- 验收：在业务配置为 OSS 的环境运行全套测试，也没有真实网络访问或外部删除；外部写操作漏出时测试直接失败。

### R2. 直接应用部署清单会回退为 local 后端，产物只存在 worker 中

- 位置：`apply/maintenance-app-deployment.yaml:14`、`:349`、`:374`、`:403`；`app.py:137`；README.md 的直接 apply 部署说明。
- 条件：按照文档直接应用该 YAML，或在 redeploy 同步完整配置后再次 apply。
- 问题：YAML 内嵌 ConfigMap 只有 Redis 配置，缺少 package_storage。程序因此采用默认 local 后端、并发 1；但 worker 的产物目录已是独立 emptyDir，与 app 的 PVC 不共享。
- 证据：将内嵌配置交给实际 `load_app_config()`，得到 `backend=local / concurrency=1`；仓库 config.yaml 的对应值为 `oss / 3`。
- 影响：任务可显示成功，但 app 无法读取 worker 产物；Pod 重建还会丢失该文件。redeploy.sh 单独同步完整配置不能消除后续 apply 覆盖的风险。
- 建议：统一配置真源，让所有受支持的部署入口得到同一份完整配置；对分离目录却配置 local 的组合加入启动校验。
- 验收：从仓库在空环境重建的有效配置与预期一致，任一 worker 完成的产物均能从 Web 下载。

### R3. OSS 上传失败仍报告成功，本地回退已不适用于分离部署

- 位置：`app.py:1409`、`:1428`，custom 对应 `:1574`、`:1589`；下载 `:2072`。
- 条件：当前 worker 独立目录部署下，上传超时、失败或 OSS 短暂不可用。
- 问题：上传返回 None 后仍写入 `complete=True / error=False`，并公布下载入口。下载接口不检查该任务的 oss_uri，先尝试给同名对象签名；签名也失败时，只能读取 app 自己的目录。
- 证据：隔离构建探针强制上传失败，最终为 `status=complete / oss_uri=null`。允许签名返回地址时接口仍 302；app 看不到产物且签名失败时返回 500。
- 影响：用户收到成功提示却拿不到包；同名历史对象存在时，还可能下载到旧产物。签名成功不能作为本次产物已上传的证明。
- 建议：OSS 是交付必需条件时，上传失败应进入可重试的交付失败状态；只有确认可访问的产物才能发布成功。恢复上传时保留本地包，并明确它属于哪个 worker/执行尝试。
- 验收：上传失败不会提供虚假的成功下载；恢复上传后不必重新拉取镜像；不同 app/worker 目录下结果一致。

### R4. 不同路径的同名镜像会被静默漏包

- 位置：`bin/pull_save.sh:112`、`:128`；`app.py:1548`。
- 条件：自定义列表同时包含 `team-a/agent:v7.1.1` 和 `team-b/agent:v7.1.1`。
- 问题：两者均映射为 `agent_v7.1.1.tar`。第二个镜像遇到已有文件后直接返回成功；后端只检查至少存在一个 tar，没有检查每个清单项都有对应产物。
- 证据：使用实际脚本配合本地 skopeo 替身，脚本退出 0，只导出 team-a，目录只有一个 tar。
- 影响：包内清单包含两个镜像，实际只有一个，最终任务仍成功。
- 建议：文件名加入路径信息或完整引用哈希；在归档前核对镜像引用与导出文件一一对应，重名不能当作成功去重。
- 验收：两份不同引用均可从包内独立导入，并保留正确 tag；清单数量与有效镜像产物相符。

### R5. 回收中断可重复入队，同一 task_id 的 slot 不能阻止重复执行

- 位置：`worker.py:75`、`:85`、`:86`；`app.py:393`。
- 条件：回收时 RPUSH 已成功，但进程在删除 processing 之前退出，或 Redis 响应丢失导致重试。
- 问题：入队和清除旧 processing 不是原子操作。下一次回收再次入队；相同 task_id 已有 slot 时又直接返回 True，使两个 worker 都能获得执行权。
- 证据：模拟 RPUSH 成功后丢失响应，第一次 queue=1、processing=1；第二次回收后 queue=2、processing=0；同一任务的两次槽位获取均返回 True。
- 影响：同节点争用/删除相同临时目录，多节点重复上传并覆盖状态。现有回收锁只能防止同时回收，不能防止中断重试。
- 建议：原子转移回收消息；执行所有权记录 worker 和 attempt，重复消息不能共享执行权，旧执行者不能完成或释放新执行者的任务。
- 验收：故障注入后任务仍能恢复，但同一时刻最多一个执行者；原有失活 slot 清理能力保留。

### R6. 日志写入异常会撤销子进程超时和取消保护

- 位置：`app.py:661`、`:667`–`:675`。
- 条件：子脚本已启动，随后 Redis 写日志或本地日志写入失败。
- 问题：退出读循环后，finally 先停止取消监听、取消 timer，再无界等待子进程。此时仍在拉取的进程不再受超时/取消控制。
- 证据：模拟日志写入抛 ConnectionError，子命令执行 1.2 秒，超时设为 0.2 秒；实际 1.21 秒后才返回异常。
- 影响：真正卡住的拉取可能长期占住 worker 和槽位，原有两小时上限不再有效。
- 建议：异常退出时先终止整个进程组，再有界等待并回收；保留原始异常，避免子进程遗留。
- 验收：Redis 写日志失败时子进程及其后代会结束；槽位释放；正常超时和主动取消仍通过回归测试。

## 5. 已有问题与需要确认的边界

以下不重复作为新发现，但后续开发需要知道：

- SSE 重试耗尽后解锁构建：`static/app.js:539`。观察失败不代表任务结束，仍存在重复提交/丢失当前跟踪的风险。
- 总览轮询无请求超时：`static/app.js:715`。一次永久 pending 会让 overviewLoading 持续为 true，自动与手动刷新都跳过。
- 构建中 V6/V7 模式切换已经被锁定，ISSUES 对应条目部分过时；channelSelect 尚未锁定，切换版本线后仍会被下一次 SSE 校准回来（`:568`）。
- 带端口 registry 仍被前端正则拒绝：`:1063`；服务端也缺少统一严格的自定义镜像校验，不能仅放宽前端。
- worker 等 slot 最多 600 秒（`worker.py:115`），短于合法构建时长。worker 多于槽位、降低并发或滚动发布时，正常排队任务可能被标记失败。
- Worker 在线展示阈值仍为 30 秒，而心跳 TTL 为 60 秒。
- 单测 FakeRedis 不实现真实 TTL；lrem/ltrim 基本为空实现，无法验证完整队列移除、日志截断和过期行为。
- 仓库凭据与客户定制升级脚本按当前项目策略保留。跨版本线交付时仍要确认包内脚本的现场仓库、组件列表和升级路径；自动填写 upgrade_version 不代表脚本已通用化。

待环境或上游契约验证的两项：

1. **OSS 下载按钮的 HEAD 前置检查。** `static/app.js:1050` 先 fetch HEAD，再导航。遇 OSS 跨域读取未放行或签名拒绝 HEAD 的环境，正常 GET 下载也会被按钮阻止。本地 HTTP 模拟已验证失败路径，但未读取真实 bucket 的 CORS 和签名方法行为，因此不写成“现网所有按钮已失效”。建议直接导航下载，用同源元数据接口承担存在性检查。
2. **缺少 make.sh 的 patch 是否允许跳过。** `get_patch_image_tag_list.sh:168` 对缺失文件静默跳过。项目承认存在空 patch/基础镜像 patch，离线无法断言缺失就是错误；需要上游定义哪些 patch 必须有清单，避免把合法空变更与数据缺失混为一谈。

## 7. 建议开发顺序与验收清单

### 第一批：建立安全、可重建的基线

先修 R1 测试外部调用隔离；再统一 config.yaml 与部署清单的配置来源，修 R2，并修发布的镜像分发和 tag 同步。同步 AGENTS、ISSUES、README 与架构说明，让后续开发不再按过时约定操作。

验收：离线单测不产生外部副作用；Linux 环境 49 项通过；直接部署与脚本发布的有效配置一致；连续两次发布后所有目标节点与仓库清单一致。

### 第二批：保证“成功”对应正确且可下载的交付物

修 R3 上传/成功状态和 R4 镜像文件唯一性；一并修完整引用解析、curl、按钮下载检查，明确 OSS 远端保留方案。

验收：上传成功、上传失败、同名旧对象、只有远端副本、多个不同路径同名镜像均有回归；实际产物逐个 docker load，检查镜像名/tag/数量；从 Web、历史列表和复制的命令都能取到同一份包。

### 第三批：补任务故障恢复

修 R5 执行所有权和原子回收、R6 子进程退出协议；随后补日志游标、阶段取消和合理的排队等待语义。保持现有槽位、失活清理、取消标记等机制的小范围修正。

验收：注入“回收入队后中断”“重复消息”“日志 Redis 异常”“worker 重启”“打包/上传取消”，确保只有一个有效执行者、没有遗留进程、槽位能够释放、日志不会无声漏掉。
